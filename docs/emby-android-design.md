# Emby Android Client 设计方案

## 1. 目标

做一个面向手机的 Emby 客户端，核心目标不是“能播”，而是：

- 界面现代，操作路径短，单手可用。
- 播放器启动快、切流快、稳定，不轻易黑屏或卡死。
- 对 Emby 常见媒体能力支持完整：直连播放、转码播放、`strm`、外挂字幕、内封字幕、音轨切换、断点续播。
- 架构上为后续真机调试、播放器内核替换、TV 版或平板版扩展预留空间。

第一阶段只做 Android 手机端，不做 iOS，不优先做下载离线和直播电视，但架构预留接口。

## 2. 产品定位

产品方向不是“全功能 Emby 设置面板”，而是“以播放体验为核心的现代客户端”。

关键词：

- 快：冷启动快，海报列表滚动稳，点开即播。
- 干净：弱化复杂后台概念，强化内容浏览和播放。
- 专业：字幕、音轨、码率、解码器、播放统计信息要做实。

## 3. 技术选型

### 客户端框架

- 语言：Kotlin
- UI：Jetpack Compose
- 架构：Clean-ish Modular Architecture
- 并发：Kotlin Coroutines + Flow
- DI：Hilt
- 网络：OkHttp + Retrofit + Kotlinx Serialization
- 本地缓存：Room
- 图片：Coil
- 翻页：Paging 3
- 后台任务：WorkManager
- 日志与埋点：Timber + 本地调试事件面板

### 播放器内核

建议采用“双内核策略”，不要把“全格式支持”压在一个播放器上。

#### 主内核

- Media3 ExoPlayer

适合：

- Android 原生集成
- 生命周期管理成熟
- DASH/HLS/HTTP progressive 支持完善
- 硬解、音频焦点、字幕轨道、画中画、后台播放能力强

#### 兼容内核

- `mpv-android` 或基于 `libmpv` 的封装

适合：

- 对部分特殊封装、字幕渲染、音频格式、网络流更宽容
- 兼容 `ass/ssa`、复杂字幕样式、外挂字幕、部分非标准流

#### 选择策略

- 默认用 ExoPlayer。
- 获取 `PlaybackInfo` 后，根据容器、编解码、字幕类型、播放失败记录决定是否切到 `mpv`。
- 首次失败自动降级到兼容内核，避免用户反复手切。
- 用户可以在播放器设置里固定某类资源使用某个内核。

这比“只用一个播放器追求完美兼容”更现实，也更接近可交付状态。

## 5. 信息架构与页面设计

### 5.0 设计对标

视觉设计以 `docs` 中提供的参考产品为主视觉基准，不做“借一点感觉”的模糊对标。

从 `docs` 里的参考图来看，这套参考方向已经比较明确：

- 深色沉浸式背景，不是传统卡片化 Material 风格
- 首页 Hero 区全屏化，海报和背景模糊叠加
- 大标题、低饱和色块、圆润悬浮底栏
- 列表卡片偏“画廊”而非“表格”
- 设置页、排序弹层都走毛玻璃和半透明浮层
- 搜索页很克制，留白多，输入区固定在下半区

这说明我们的客户端视觉基调应该明确走这类“内容沉浸 + 轻拟物悬浮控件”路线，而不是标准 Android 设置页拼装。

### 5.0.1 对标范围

需要吸收的是这套参考界面语言：

- 深色渐变背景
- 大标题和大面积 Hero
- 悬浮底部导航
- 毛玻璃或半透明浮层
- 低密度、偏展陈式的内容布局

不直接照搬的是它的业务信息结构：

- 我们保留 Emby 的媒体库、详情、播放、字幕、音轨这些专业能力
- 只借它的视觉秩序、控件形态和沉浸感
- 不能因为追求风格，把播放器效率和媒体信息可读性做弱

## 5.0 视觉系统

先定一套足够明确且贴近参考图的视觉语言，后续页面实现时就不会漂。

### 视觉关键词

- 冷静
- 悬浮
- 有纵深
- 沉浸
- 信息密度克制
- 带一点影院感和播放器感

### 配色建议

- 主背景：`#0A0910`
- 渐变上层：`#1B2148`
- 渐变下层：`#41172E`
- 卡片背景：`#221F2C`
- 浮层背景：`#2B2734CC`
- 强调色：`#8DE35A`
- 辅助强调色：`#FF9F1C`
- 文字主色：`#F7F3F8`
- 文字次色：`#B7AFC0`

原则：

- 背景必须是分层渐变，不做纯黑或纯蓝平铺
- 绿色强调色只用于“在线、播放、已连接、主 CTA”
- 橙色只用于状态点、警告和播放中动态提示
- 紫红渐变只作为氛围色，不承担关键信息表达
- 文本白色不要打满纯白，避免屏幕刺眼

### 排版建议

- 中文优先使用系统无衬线，保证兼容性和清晰度
- 标题强调靠超大字号和高字重，参考图里标题占比很高
- 大标题用于 Hero 区、频道页和搜索页
- 元信息统一做“小字 + 低对比”，不和标题抢视觉
- 正文区控制字重层级，避免整个界面都是半粗体
- 中文标题可以更激进，英文和数字则更收一点，避免画面散

### 组件风格

- 卡片统一大圆角，尽量不出现硬边矩形
- 底部导航做“浮动胶囊”而不是贴底栏
- 弹层采用毛玻璃或半透明深色浮层，带弱描边
- 播放器控制按钮偏实心，不做细线图标风
- 操作按钮优先圆形或胶囊形
- 进度条使用更粗的可触控轨道，保证拖动手感
- 列表排序菜单做大圆角浮层，不做原生下拉菜单观感
- 避免直接使用默认 Material 3 `TopAppBar`、`NavigationBar`、`AlertDialog` 观感

### 动效原则

- 首页卡片分组渐入
- Hero 背景切换时做轻微缩放和透明度过渡
- 播放页控制层淡入淡出，不做夸张位移动画
- 列表切换和筛选面板动画要短，控制在 180ms 到 240ms
- 首次开播允许一个轻微缩放过渡，强调“进入沉浸态”
- 浮动底栏在滚动时可轻微收缩，但不应完全消失

### 借鉴与修正

参考产品里有几个优点应该明确吸收：

- 首页用大海报 Hero 建立强入口
- 底部导航和搜索按钮悬浮，界面更轻
- 设置页采用大块分组卡片，比传统列表更现代
- 排序和筛选面板有明确层级，不像系统菜单那样生硬

同时也有几点不建议直接照搬：

- 某些页面顶部信息压在复杂海报上，文字可读性偏弱
- 搜索页留白很大，但如果无推荐和历史，会显得空
- 部分列表卡片文字过小，中文环境下会更吃亏
- 底部悬浮搜索按钮在部分页面会遮挡海报角标和操作区

所以实际实现时要保留这套风格方向，但提升可读性、触控安全区和信息效率。

## 5.1 首页

首页不是传统“密集海报墙”，而是接近参考首页那种“海报沉浸 + 内容带”的内容流。

布局建议：

- 顶部：服务器切换、搜索、用户头像
- Hero 区：继续观看中的一项，显示大标题、年份、类型、评分、简介和“继续播放”
- Hero 下方用圆点或横条表示轮播位置
- 内容带：今日趋势、继续观看、最近新增、电影、剧集、合集
- 底部导航：首页 / 追剧 / 设置，搜索作为独立悬浮按钮也可以纳入备选
- 顶部和底部控件都要明显悬浮于背景之上，不贴边死板排布

视觉方向：

- 默认深色主题优先，浅色仅作为后备
- 背景用低对比渐变叠加海报模糊，不用纯黑平铺
- Hero 区文字必须有遮罩层，保证在复杂画面上仍可读
- 卡片圆角偏大，文字层次清晰，减少边框
- 首页第一屏优先做气氛和入口感，信息完整性放到第二屏内容带承接

## 5.2 媒体库

媒体库要以“快定位”为目标。

关键能力：

- 顶部超大分类标题，形成频道感
- 多维筛选：类型、年份、评分、未看、高清、字幕可用
- 排序按钮做成独立胶囊按钮，点击弹出毛玻璃面板
- 支持列表/双列海报切换
- 默认优先双列或三列海报流，而不是文本列表
- 滚动时顶部筛选条吸附
- 大库分页加载，优先显示文字骨架和低清缩略图
- 频道页要有明显“被策展过”的感觉，不能只是朴素网格

## 5.3 详情页

详情页要服务播放决策，不只是展示简介。

核心区域：

- 顶部背景图 + 海报或关键帧图
- 一键播放 / 继续播放 / 选择版本
- 媒体信息：分辨率、编码、时长、音轨、字幕
- 简介区默认两到三行，可展开
- 剧集列表
- 更多动作：播放队列、下载字幕、标记已看、刷新元数据

细节要求：

- 返回按钮和次级操作按钮要悬浮在顶部安全区
- 标题可做超大字，但副信息必须保持规整
- 如果是剧集或合集，详情页首屏必须优先给“继续看”和“下一集”

## 5.4 播放页

播放器是产品核心，界面要克制。

默认交互：

- 单击显示/隐藏控制层
- 左右半屏双击快退/快进
- 纵向滑动左侧调亮度，右侧调音量
- 横向滑动调进度，带缩略图预览

控制层布局：

- 顶部：返回、标题、当前服务器质量状态
- 中部：播放/暂停、快退/快进
- 底部：进度条、时间、选集、字幕、音轨、清晰度、更多

更多面板：

- 播放器内核切换
- 解码模式
- 倍速
- 字幕样式
- 音频增益
- 播放统计信息

视觉细节：

- 控制层使用半透明暗色，不遮满整个画面
- 快进快退反馈做大号数字或箭头动画，便于盲操作
- 清晰度、字幕和音轨入口优先放到底部主操作区，不藏太深

## 5.5 搜索页

搜索页直接参考这套布局方向，但要补足内容承载。

布局建议：

- 顶部保留大标题“搜索”
- 输入框放在中下区域，维持轻量感
- 未输入时展示搜索历史、最近播放、热门标签
- 输入后切到结果页状态，结果用海报瀑布流或分组列表

原则：

- 静态空白可以有，但不能空到只剩输入框
- 搜索取消按钮保持圆形独立按钮，触感明确
- 输入框要支持语音、清空、服务器范围切换预留

## 5.6 设置页

设置页建议基本沿用这套方向，因为它比常见 Android 设置页更统一。

布局建议：

- 顶部大标题
- 同步、播放、界面、字幕、网络、调试分组卡片化
- 关键功能用大卡片强调，比如会员、实验功能、播放器内核模式

原则：

- 设置项不要做密集小字列表
- 每组控制在 3 到 6 项，超过就拆组
- 能切换状态的项目，直接在右侧显示当前状态，不要全部点进去才知道

## 6. Emby 接入设计

### 核心接口

围绕以下能力组织数据流：

- 服务器发现与连接
- 用户认证
- 首页/媒体库/搜索接口
- `PlaybackInfo` 获取
- 进度上报
- 字幕流和外部字幕获取
- 用户配置同步

### 账户与服务器

支持：

- 多服务器保存
- 单服务器多用户
- 最近连接服务器置顶
- 证书异常、反向代理异常的诊断提示

### 播放前决策

在点播前执行一次轻量“播放预判”：

1. 请求 Emby `PlaybackInfo`
2. 判断能否 Direct Play
3. 判断是否需要服务器转码
4. 选择播放器内核
5. 组装播放源、请求头、字幕轨、音轨、章节信息

这样播放器页打开前就有明确播放方案，不把复杂逻辑堆到 UI 生命周期里。

## 7. `strm` 支持方案

`strm` 必须作为一等公民处理，不能只当普通文件。

### 设计原则

- 服务端若已解析为可播放 URL，优先走 Emby 提供的播放路径。
- 对外部远程流，保留原始 URL、重定向、Cookie、Referer、User-Agent 注入能力。
- 兼容 HLS、DASH、普通 HTTP 文件流以及部分站点跳转链。

### 客户端处理链路

1. 从 Emby 元数据识别 `strm` 项
2. 请求 `PlaybackInfo`
3. 提取最终媒体源与所需请求头
4. 判断流类型
5. 交给 ExoPlayer 或 mpv
6. 若主内核失败，自动 fallback

### 风险点

- 某些 `strm` 指向资源站，需要特殊 Header
- 某些源有短时效签名，不能长期缓存
- 某些站点字幕与主流不同源，需要额外匹配策略

所以播放器层必须支持“每个媒体源独立 Header 集合”，不能只做全局请求头。

## 8. 字幕设计

字幕不能只是“能开关”，而要完整。

### 支持范围

- 内封字幕
- 外挂字幕
- 本地选择字幕文件
- Emby 服务端提供字幕流
- 文本字幕：SRT / ASS / SSA / VTT
- 图形字幕：PGS / SUP

### 功能要求

- 自动匹配首选语言
- 自动加载同名外挂字幕
- 字幕偏移调节
- 字幕大小、描边、底色透明度调节
- 双字幕能力预留
- 播放中无感切换字幕轨

### 内核策略

- ExoPlayer 负责标准文本字幕和常规轨道管理
- 复杂 `ASS/SSA`、图形字幕或渲染异常场景优先交给 mpv
- 对不支持原生渲染的格式，可回退服务端烧录字幕转码

### 字幕来源优先级

1. 用户上次选择
2. 与用户语言匹配的外挂字幕
3. 默认字幕轨
4. 无字幕

## 9. 音视频格式支持策略

“完美支持各种格式”在 Android 上不能靠一句口号实现，要做分层能力管理。

### 常见目标格式

- 容器：MP4 / MKV / WebM / TS / M2TS / AVI
- 视频：H264 / H265 / AV1 / VP9
- 音频：AAC / Opus / AC3 / EAC3 / DTS / FLAC / TrueHD

### 处理原则

- 优先硬解，失败再软解
- 设备能力动态探测，不写死机型表
- 对高风险组合建立兼容策略

例如：

- `TrueHD` 在很多手机上不可直出，需要转码或兼容内核
- `PGS` 在 ExoPlayer 中体验不稳定时，需要 fallback
- 某些 `10-bit HEVC` 在中低端芯片上会掉帧，需要自动建议转码

### 能力探测

首次启动采集设备解码能力：

- `MediaCodecList`
- 分辨率/色深/编解码支持
- 音频 Passthrough 可用性

生成本机 `DevicePlaybackProfile`，供播放决策复用。

## 10. 性能优化设计

性能从一开始就要作为架构要求。

### 列表性能

- 首页和媒体库分页化
- 海报请求使用合适尺寸，不拉原图
- 视图稳定 key，减少重组
- 详情页分块加载，不阻塞首屏

### 播放启动速度

- 详情页预请求 `PlaybackInfo`
- 预热 DNS / TCP / TLS 连接
- 预构建播放器实例池，但池大小严格受控
- 首帧时间单独埋点

### 内存控制

- 海报缓存分级
- 离开详情页及时释放背景大图
- 播放页退出时显式释放字幕与缩略图缓存

### 网络策略

- 支持 `Range` 请求
- 支持断线重连
- 对弱网环境动态调整缓冲策略
- 对大码率直连流增加网络测速和开播预警

### 可观测性

埋点至少要有：

- 首页首屏耗时
- 媒体库滚动掉帧率
- 首帧时间
- 卡顿次数
- 播放失败率
- 播放器 fallback 触发率

## 11. 真机调试方案

接入真实手机后，调试流程建议标准化。

### 调试能力

- `adb` 安装与日志抓取

### 重点验证项

- 断网重连
- 锁屏、后台、来电打断恢复

## 14. 第一版结论

如果目标是真正可用、可长期维护的 Emby 手机客户端，建议路线是：

- Android 原生 Kotlin + Compose
- ExoPlayer 为主，mpv 为兼容后备
- 先把播放决策层设计扎实，再做 UI 打磨
- 把 `strm`、字幕、播放失败 fallback 当成核心能力，不当边角功能

这样做，后面接真机调试时我们能很快定位问题，也更容易把“能播”推进到“播得稳、播得全、播得顺”。
